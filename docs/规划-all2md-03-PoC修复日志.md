## 2026-08-08 · 修复批次 #1（用户测试反馈，三项问题）

### 修复 1：PoC-01 · Word → HTML 乱码

| 字段 | 内容 |
|------|------|
| **日期** | 2026-08-08 |
| **问题** | mammoth 输出的 HTML 在浏览器中打开显示为乱码，中文完全无法阅读 |
| **根因** | mammoth 生成的 HTML **不包含 `<meta charset>` 声明**。浏览器在本地打开无 charset 的 HTML 文件时，会按浏览器的默认编码（如 GBK）解析，导致 UTF-8 中文乱码 |
| **修复** | 在 `poc-01-mammoth.js` 输出环节，检测 `<head>` 标签并注入 `<meta charset="UTF-8">`；若无 `<head>` 则插入文档最前面 |
| **代码位置** | `poc/poc-01-mammoth.js` · 输出区域 |
| **验证** | 运行后 HTML 开头出现 `<meta charset="UTF-8">`，浏览器正常显示中文 |
| **M1 影响** | 正式开发时 turndown 吃的是 HTML 字符串（内存），不需要写文件，所以不需要 charset。但如果有导出 HTML 的调试/备选功能，需要记住注入 charset |

### 修复 2：PoC-02 · PPT 文字被不规则切断

| 字段 | 内容 |
|------|------|
| **日期** | 2026-08-08 |
| **问题** | PPT 转换后每行文字被切成两三段，比如"上海金堂轻纺新材料科技有限公司"被切成 3 行，阅读困难 |
| **根因** | PPTX 的 XML 结构中，**同一文本框**内不同格式的文字会产生多个 `<a:r>`（文本运行）+ `<a:t>`（文字片段）。原 `parseSlideXml` 用全局正则 `/<a:t[^>]*>([^<]*)<\/a:t>/g` 逐个提取 `<a:t>`，每个独立输出一行，导致同一段落的文字被拆散 |
| **修复** | 重写 `parseSlideXml`：改为**按 `<a:p>`（段落）分组**，每个段落内合并所有 `<a:t>` 拼接成完整句子再输出 |
| **正确结构** | `<a:p>`（段落）→ 多个 `<a:r>`（文本运行，各有不同格式）→ 每个 `<a:r>` 一个 `<a:t>`（文本）。正确做法是 `a:p` 内 `a:t` 拼接，而非全部 `a:t` 独立输出 |
| **代码位置** | `poc/poc-02-pptx.js` · `parseSlideXml()` 函数 |
| **验证** | Slide 1 "以ESG理念成为全球绿色低碳技术创新服务领导者" 完整一行；"上海金堂轻纺新材料科技有限公司" 完整一行 |
| **M1 影响** | 正式开发时必须继承此做法——按 `<a:p>` 分组是 PPTX 文本提取的正确方式 |

### 修复 3：PoC-02 · PPT 图片未提取

| 字段 | 内容 |
|------|------|
| **日期** | 2026-08-08 |
| **问题** | PPT 转换结果中统计到了图片引用数，但没有实际提取和保存图片文件 |
| **根因** | 原 PoC 只从 `<a:blip r:embed="...">` 提取了关系 ID（`rId`），但没有解析关系文件（`.rels`）将 rId 映射到 `ppt/media/` 下的实际文件路径，也没有读取二进制数据 |
| **修复** | 新增 `resolveSlideImages()` 函数：读取 `ppt/slides/_rels/slideN.xml.rels`，匹配 `Relationship Id="rId" Target="../media/xxx.png"` 获取图片路径，然后从 zip 中提取二进制保存到输出目录。主函数中添加跨幻灯片去重逻辑 |
| **代码位置** | `poc/poc-02-pptx.js` · `resolveSlideImages()` + 主函数图片收集循环 |
| **验证** | 28 张图片成功提取到 `poc-output/poc-02-images/`（24 PNG + 4 JPEG） |
| **M1 影响** | 正式开发时需将此逻辑集成到 pptx-converter.ts，图片可按设置保存到 vault 附件目录 |

### 修复 4：PoC-03 · PDF 文本全部挤在一起

| 字段 | 内容 |
|------|------|
| **日期** | 2026-08-08 |
| **问题** | PDF 转换后所有文字连成一片，没有换行、没有分段，阅读困难 |
| **根因** | 原 PoC 用 `textContent.items.map(item => item.str || '').join(' ')` 将所有文本项用空格连接。pdf.js 的 `textContent.items` 是扁平列表，每个 item 有 `str`（文字）+ `transform[4]`（X 坐标）+ `transform[5]`（Y 坐标）。忽略位置信息 → 丢失所有结构 |
| **修复** | 新增 `buildPageParagraphs()` 函数，利用每个 textItem 的 Y 坐标重建页面结构：<br>① 按 Y 坐标分组（容差 0.5×平均字高）→ 同 Y = 同一行<br>② 每行内按 X 坐标排序后拼接文字<br>③ Y 间距 > 2.2×字高 → 判定为新段落（插入空行） |
| **代码位置** | `poc/poc-03-pdf.js` · `buildPageParagraphs()` 函数 |
| **验证** | 第 2 页的"模组介绍"、"使用说明"、"特殊说明"、"声明"正确分段；段落内换行保留 |
| **遗留限制** | 多栏 PDF 布局（如第 3 页双栏）会导致两栏文字交错——这是所有 PDF 文本提取工具的经典难题，仅靠坐标分析无法完美解决，需在 M2/M3 考虑段落排序算法或 AI 后处理 |

### 修复 5（未完成）· PoC-03 · PDF 图片提取

| 字段 | 内容 |
|------|------|
| **日期** | 2026-08-08 |
| **问题** | PDF 转换后没有图片 |
| **根因** | pdf.js 的 `page.objs` 图像对象 API **仅在 Worker 模式下可用**。PoC 为模拟 Obsidian 沙箱降级环境使用了 `disableWorker: true`，此模式下 `page.objs.get()` 无法获取图片二进制数据 |
| **当前状态** | 已在代码中添加 `extractPageImages()` 尝试提取，返回空数组（expected） |
| **M1 方案** | 在 Obsidian 中加载 pdf.js worker bundle（约 3MB），以 base64 内联或 data URI 方式提供 `workerSrc`。Worker 加载成功后 `page.objs` 恢复正常，图片即可提取。此方案已在策划案风险表（第 275 行）中记录 |
| **替代方案** | 如果不希望引入 worker bundle 增加插件体积，可用 Canvas 渲染每页截图（`page.render()` + `OffscreenCanvas`），但此方案依赖浏览器 Canvas API，需验证 Obsidian 沙箱是否支持 |
